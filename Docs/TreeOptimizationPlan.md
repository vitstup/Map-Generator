# План оптимизации деревьев

Реализация выполнена; итоговые настройки, проверки и измерения описаны в [TreeOptimizationResults.md](TreeOptimizationResults.md).

Дата обследования: 30 октября 2026. Основание: исходный код, сохранённые ассеты и чтение данных открытого MainScene через Unity Editor. Реализация оптимизации в рамках этого обследования не выполнялась.

## Вывод

Дополнительные LOD нужны прежде всего крупной сосне, большому клёну и гинкго. Но необходимы также более дешёвые материалы ближнего/среднего плана и плавные переходы в собственном рендерере. Одно лишь добавление последнего mesh LOD сейчас почти ничего не изменит: часть уже имеющихся уровней отсекается общим порогом перехода в импостор.

Рекомендуемый порядок: измерения → пилот на двух тяжёлых видах (меши + материалы) → переходы и пороги → независимые LOD теней → распространение на остальные виды. Occlusion culling и дальнейшая перестройка подачи draw calls — следующий этап, если замеры покажут необходимость.

## Что установлено

- Unity 6000.3.17f1, URP 17.3.0. В открытом редакторе: AMD Radeon RX 7700 XT, Direct3D12, PC_RPAsset, LOD Bias = 2.
- В текущем MainScene 163 225 деревьев: 8 084 на основном Terrain, 45 657 на окружающем и 109 484 на горизонте. Это количество размещений, а не число видимых деревьев в кадре.
- Terrain хранит размещения, но его рендеринг деревьев отключён. Близкие деревья рисует InstancedTreeRenderer через Graphics.RenderMeshInstanced; дальние — IndirectTreeImpostors через Graphics.RenderMeshIndirect с compute culling.
- Уже существуют 2–3 исходных mesh LOD на вид, GPU instancing, пространственная сетка ближних деревьев, frustum/distance/screen-size culling и дальние импосторы. Повторное внедрение instancing не является основной задачей.

Треугольники на дерево, включая отдельный renderer ветвей:

| Вид | LOD0 | LOD1 | LOD2 |
|---|---:|---:|---:|
| Pine_01 | 15 588 | 7 980 | 4 086 |
| Pine_02 | 3 888 | 2 104 | 1 082 |
| Pine_03 | 1 888 | 1 026 | 560 |
| Maple_01 | 14 164 | 8 702 | 3 420 |
| Maple_02 | 594 | 530 | — |
| Ginko_01 | 6 280 | 3 086 | — |

- Mesh Screen Height = 0.20. Значение сравнивается с размером, уже умноженным на LOD Bias. При текущем bias = 2 переключение в импостор происходит примерно на 10% расчётного экранного размера. Это приближение через LODGroup.size, максимальный масштаб и расстояние до центра, а не измеренная высота силуэта в пикселях.
- При обычном hybrid path и maximumLODLevel = 0 LOD2 у Pine_01, Pine_03 и Maple_01 вообще не выбирается: его диапазон уже перекрыт импостором. У Pine_02 LOD2 доступен только в очень узком диапазоне 0.20–0.20222.
- Выбор LOD дискретный. Код отправляет только один уровень, не передаёт коэффициент перехода на экземпляр и не создаёт область совместной отрисовки mesh/impostor. CrossFade исходных LODGroup не переносится в эту систему. В URP target исходного Foliage Shader Graph m_SupportsLODCrossFade = false; простой смены Fade Mode в prefab недостаточно.
- Все пять материалов близких деревьев используют Synty/Foliage: alpha clipping, Cull Off, включённые настройки нескольких видов ветра, процедурного цвета, normal map листвы или ствола. Сохранённые настройки указывают на возможную высокую стоимость, но не доказывают, какая именно часть шейдера ограничивает GPU.
- На PC включены SSAO и мягкие тени с четырьмя каскадами. TreeBuilder задаёт 100 м теней, но рендерер ограничивает их shadowDistance URP, то есть сейчас 50 м. Уже существует ограничение теней, его не нужно внедрять заново.
- Импостор — один quad, 24 ракурса: 8 азимутов × 3 высоты, тайл 256 × 256. Освещение запечено отдельным солнцем; живого ветра и теней нет. Это потенциальный источник скачка цвета, движения и объёма при переключении. Выше 16 расчётных пикселей шейдер смешивает четыре ракурса, ниже — выбирает один.
- Команда Bake Optimized Tree LODs сейчас запекает импосторы и собирает ссылки на существующие меши; новые упрощённые 3D-меши она не генерирует.

## 1. Получить воспроизводимую исходную точку

Подготовить фиксированный маршрут и несколько камер: внутри рощи, у её края, взгляд вдоль нескольких крон, обзор сверху и дальняя панорама. Зафиксировать карту/seed, разрешение, FOV, качество и положения камер. Основную оценку вести в standalone development build на целевой видеокарте с прогревом и без ограничения FPS.

Снимать GPU frame time, CPU frame time, стоимость проходов, количество видимых деревьев каждого LOD, треугольники/вершины, draw calls и overdraw. Отдельно проверять моменты перехода и движение камеры, а не только неподвижный кадр.

Диагностические A/B-прогоны при тех же размещениях:

1. Деревья включены/выключены, сохраняя остальную сцену.
2. Те же деревья без отбрасывания теней.
3. Те же меши с простым диагностическим alpha-clipped материалом с той же маской.
4. Фиксированные mesh LOD, затем impostor path.
5. Меньшее разрешение для оценки зависимости от числа закрашиваемых пикселей.

Frame Debugger использовать для состава проходов, GPU Profiler/совместимый GPU capture — для времени. Исходный TreeCostProfile измеряет Camera.Render + синхронный ReadPixels: это суммарное время эксперимента, не чистый GPU time. Текущий запрос статистики редактора вернул gpuFrameTimeMs = 0, поэтому доказанного распределения GPU затрат пока нет.

Результат этапа: таблица стоимости близкого леса с разделением гипотез о геометрии, пиксельном шейдере/overdraw и тенях.

## 2. Пилотная цепочка LOD для Pine_01 и Maple_01

Сначала создать варианты на копиях мешей этих двух видов. Сохранить исходный подробный уровень для очень близкого осмотра, а обычный ближний и средний план обслуживать более дешёвыми уровнями.

Начальные бюджеты для эксперимента, не окончательная спецификация:

| Представление крупного дерева | Бюджет треугольников | Назначение |
|---|---:|---|
| Исходный подробный mesh | текущий | Только очень близко, если детализация видна |
| Оптимизированный ближний mesh | 3 000–6 000 | Убрать избыточную внутреннюю геометрию, сохранить внешний вид |
| Средний mesh | 800–2 000 | Силуэт, объём и узнаваемая форма кроны |
| Дальний объёмный mesh | 150–600 | Дешёвый мост к импостору |
| Импостор | 2 | Маленькие деревья на экране |

Для Ginko_01 впоследствии подготовить собственные промежуточные уровни. Для уже дешёвого Maple_02 не добавлять уровни механически: исходные 594 → 530 треугольников дают мало геометрической экономии, важнее материал и переход.

При генерации сохранять UV, vertex colors/маски ветра, нормали, pivot, масштаб, основные развилки и плотность силуэта. Для листвы сравнить обычную децимацию с удалением внутренних/мелких кластеров и укрупнением карточек. Меньшее число треугольников само по себе не гарантирует меньше overdraw: несколько крупных почти прозрачных плоскостей могут ухудшить результат.

Первым кандидатом проверить встроенный в Unity 6.3 MeshLodUtility на копиях мешей. Если он портит листву или не достигает нужной экономии, использовать отдельные упрощённые Mesh и более управляемый способ подготовки крон. Не менять импорт всех исходных Synty FBX на первом эксперименте.

Важное ограничение интеграции: Graphics.RenderMeshInstanced и Graphics.RenderMeshIndirect не выбирают native Mesh LOD автоматически; для него требуется явный RenderParams.forceMeshLod. Возможны два пути: явно выбирать native mesh LOD index в существующих батчах либо запекать отдельные Mesh в TreeRenderLibrary. Выбор сделать по качеству пилота и удобству назначения материалов. Простая галочка Generate mesh LODs не завершает задачу.

## 3. Удешевить материалы одновременно с геометрией

Сделать варианты материалов/шейдера по дальности. На ближнем уровне сохранить нужные художественные свойства; на среднем последовательно убрать дорогой процедурный цвет, лишние normal map, сложные режимы ветра и ненужные световые эффекты. Сначала подтвердить вклад каждого изменения замерами.

Для среднего уровня рассмотреть простой diffuse-шейдер с текстурой, vertex color, простым ветром и согласованным приёмом теней. Реально исключать вычисления из варианта шейдера: нулевой параметр в материале не всегда означает отсутствие работы на GPU.

Ствол и непрозрачные ветви там, где это позволяет модель, рисовать opaque с backface culling; двусторонний alpha clip оставить необходимой листве. Проверить цену дополнительного draw call прежде, чем дробить каждый mesh. Убедиться, что новые материалы работают в текущем режиме URP, SSAO, Depth/DepthNormals и ShadowCaster.

Результат этапа: ускорение обычного близкого леса, а не только дальнего горизонта. Если стоимость определяется главным образом пикселями, приоритет получает этот этап, а не агрессивная децимация.

## 4. Перестроить переходы в собственном рендерере

После появления дешёвых промежуточных уровней настроить пороги по виду дерева и экранному размеру. Отделить желаемую точку перехода в импостор от случайного влияния общего LOD Bias; формально определить, какие пороги используют bias.

Снижать mesh/impostor threshold только после проверки стоимости новой цепочки. Более дальнее использование прежних тяжёлых мешей увеличит число mesh-деревьев и может ухудшить производительность. Начальные варианты перехода в импостор — несколько процентов экрана; окончательные значения подобрать по виду, углу камеры и разрешению.

Реализовать короткую область dither cross-fade для mesh → mesh и mesh → impostor: одновременно рисуются только два соседних представления. Передавать коэффициент на экземпляр, сохраняя instancing, и использовать согласованные маски исчезновения/появления. Синхронизировать границы CPU mesh culling и GPU impostor culling, иначе возникнут пропуски или двойные деревья.

Маска и ветер должны быть согласованы в цвете, глубине, нормалях и тенях. Проверить без TAA: в текущем PC-профиле MSAA выключен, поэтому нельзя рассчитывать, что сглаживание скроет зерно. Ограничить ширину перехода: два уровня временно увеличивают геометрическую стоимость.

Небольшой разброс порогов по стабильному ID дерева может убрать одновременное переключение целой рощи. Гистерезис добавлять при обнаруженном дребезге на границе; он сам по себе не сглаживает смену формы. При temporal fade обеспечить обновление коэффициентов и в неподвижной камере, несмотря на существующий cache.

## 5. Согласовать импосторы с последним mesh LOD

Сравнить пары изображений одного дерева при одинаковой камере/освещении: геометрия перед переходом и импостор после него. Проверить положение основания, размер и объём кроны, яркость, оттенок и туман. Настроить baker относительно финального вида дерева и освещения сцены.

Устранить заметный скачок ветра: затухание движения до статичного импостора либо очень дешёвое согласованное движение дальнего представления. Важнее сначала исправить момент переключения, чем увеличивать разрешение всего атласа.

Если на допустимом размере всё ещё заметны повороты плоскости/смешение силуэтов, отдельно сравнить больше ракурсов и depth/octahedral impostor. Это усложнение принимать только после проверки качества и GPU/памяти. Также проверить переход между одним и четырьмя texture samples около 16 пикселей.

## 6. Независимое качество теней

Разделить выбор видимого LOD и shadow LOD. Для близкого дерева использовать более простой shadow mesh и минимальный alpha-clipped ShadowCaster с тем же базовым ветром; для среднего плана — ещё более дешёвый силуэт. Проверить отсутствие лишнего caster от видимой геометрии, чтобы не удвоить работу.

Измерить чувствительность к 4 каскадам и качеству soft shadows; оставить такие изменения отдельным профилем качества, поскольку они затрагивают всю сцену. При переходе на импостор не допускать неожиданного исчезновения тени внутри её полезной дистанции. Отдельно проверить деревья за границей экрана, отбрасывающие видимую тень.

## 7. Дальнейшие меры — по результатам

- Сортировка пространственных батчей примерно от ближних к дальним может улучшить depth rejection; проверить отдельно для mesh и alpha-clipped импосторов, не вводя дорогую полную сортировку экземпляров каждый кадр.
- Текущий culling не проверяет закрытие деревьев рельефом. Если значителен рендеринг скрытых лесов, оценить консервативный Hi-Z/terrain occlusion с защитой от ошибочного исчезновения при движении камеры. Кроны с отверстиями — ненадёжные сплошные occluders.
- Встроенный GPU Occlusion URP связан с GPU Resident Drawer. Он не является готовым переключателем для текущих собственных indirect buffers; его использование потребует отдельной проверки/интеграции.
- Перевод ближних мешей на GPU-driven culling/indirect полезен, если ограничивает CPU или подготовка батчей. Уже существующий instancing не оправдывает такую перестройку ради предполагаемого GPU ускорения без замеров.

## Критерии готовности

1. Сравнение до/после на одинаковых размещениях и маршруте, включая близкий лес и кадры переходов.
2. GPU frame time и его высокие перцентили улучшаются в проблемных близких видах; CPU и дальняя панорама не получают существенной регрессии. Числовой бюджет согласовать по baseline и целевому FPS/разрешению, а не обещать заранее.
3. При медленном приближении, отдалении, боковом движении и обзоре сверху нет резких скачков формы, цвета, тени, дыр и двойных деревьев.
4. Силуэт и стиль проверены на всех шести видах; low-poly характер сохранён, кроны не редеют неожиданно.
5. Нет новых объектов/материалов на каждый экземпляр, GPU readback в render loop и покадровых аллокаций; ресурсы освобождаются при rebuild/disable.
6. Обновлены TreeChecks: текущие проверки требуют точного совпадения уровней, мешей и порогов с исходными Synty LOD, что конфликтует с новой цепочкой. Вместо этого проверяются целостность новой библиотеки, диапазоны, сохранность исходных ассетов и работа fallback без compute.
7. Генерация новых ассетов воспроизводима; Bake и EnsureLibrary не перезаписывают утверждённые новые уровни исходными. Проверены повторная сборка карты, Game/Scene камеры и fallback без compute.
